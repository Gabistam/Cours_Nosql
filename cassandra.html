Le modèle Orienté Colonnes

Cassandra est une base distribuée, sans maître conçue pour absorber d'énormes volumes d'écritures sur des centaines de nœuds. Son modèle « wide-column » et son langage CQL ressemblent à du SQL, mais la logique est inversée : on modélise autour des requêtes, pas autour des données. Cas d'usage roi : les séries temporelles et l'analytics.

⚡ Pourquoi Cassandra pour l'analytics ?

L'analytics (vues produit, clics, événements) a un profil radicalement différent du catalogue ou du panier :

CritèreMongoDB (catalogue)Cassandra (analytics)
Profil de chargeLecture dominanteÉcriture massive
Volume20 produits (stable)Millions d'événements / jour
Forme des donnéesDocuments richesSéries temporelles append-only
ScalabilitéVerticale / replica setHorizontale linéaire
RequêtesFlexibles, ad-hocConnues à l'avance
DisponibilitéMaster + replicasMasterless (pas de SPOF)
Règle empirique : Cassandra quand on écrit énormément, que les données sont des séries temporelles append-only, et qu'on connaît ses requêtes à l'avance. À éviter pour des requêtes ad-hoc ou des jointures.

🏛️ Architecture : l'anneau sans maître

💍
Ring & peer-to-peer
Pas de nœud maître

Tous les nœuds sont égaux et organisés en anneau. N'importe lequel peut recevoir une requête (le coordinator) et la router. Aucun point unique de panne : si un nœud tombe, les autres continuent.

🔀
Partitionnement par hash
La partition key décide du nœud

Cassandra hache la partition key pour déterminer quel nœud stocke la donnée. Bien choisir cette clé = répartir uniformément la charge et éviter les hot partitions.

📑
Réplication
replication_factor

Chaque donnée est copiée sur N nœuds (RF=3 typiquement en prod). En TP local on utilise RF=1 (un seul nœud). C'est ce qui donne la tolérance aux pannes.

⚖️
Niveaux de cohérence
ONE · QUORUM · ALL

Cassandra est « AP » (théorème CAP) et propose une cohérence tunable par requête : ONE (rapide), QUORUM (équilibré), ALL (sûr mais lent).

PRIMARY KEY = (partition key, clustering columns). La 1re partie (entre parenthèses si composite) place la donnée ; les suivantes la trient. C'est la notion à maîtriser.

📈 Modéliser une série temporelle

Le pattern « wide row » : une partition par produit, et chaque vue est une ligne triée par horodatage décroissant. Lire les dernières vues d'un produit = lire une seule partition, séquentiellement. Ultra-rapide.

cql · table série temporelle
CREATE TABLE product_views (
  product_id text,
  view_time timestamp,
  session_id text,
  PRIMARY KEY ((product_id), view_time)
) WITH CLUSTERING ORDER BY (view_time DESC);

product_id = partition key (toutes les vues d'un produit ensemble). view_time = clustering column triée DESC (les plus récentes d'abord).

🧭 Le renversement mental : « query-first »

En SQL on normalise, puis on écrit les requêtes. En Cassandra c'est l'inverse : on liste d'abord les requêtes, puis on crée une table par requête, quitte à dupliquer les données.

❌ Réflexe SQL
Une table normalisée + jointures + WHERE arbitraire. → Impossible : pas de JOIN, WHERE limité à la clé primaire.
✅ Réflexe Cassandra
« Je veux le top produits du jour » → table views_by_day dédiée. « Les vues récentes d'un produit » → table product_views dédiée.
La dénormalisation est normale ici. Le disque est bon marché, les écritures sont rapides : dupliquer la donnée dans plusieurs tables est la bonne pratique, pas un anti-pattern.

CQL fondamental

cqlsh · sportshopy
-- INSERT (un INSERT = un UPSERT en Cassandra)
INSERT INTO product_views (product_id, view_time, session_id)
  VALUES ('p-run-001', toTimestamp(now()), 'sess-42');

-- SELECT : WHERE doit cibler la partition key
SELECT * FROM product_views WHERE product_id = 'p-run-001';

-- Limiter aux 10 dernières (déjà triées DESC)
SELECT view_time, session_id FROM product_views
  WHERE product_id = 'p-run-001' LIMIT 10;
Piège SQL : SELECT * FROM product_views WHERE session_id = '...' échoue. On ne peut filtrer que sur la partition key (et les clustering columns dans l'ordre). Pour filtrer par session, il faudrait une autre table dédiée.

🔢 Les counters pour les agrégats

Pour compter les vues par jour, Cassandra propose le type spécial counter : un UPDATE ... SET x = x + 1 atomique et distribué.

cqlsh
CREATE TABLE views_by_day (
  product_id text,
  day date,
  views counter,
  PRIMARY KEY ((product_id), day)
);

-- Incrémenter le compteur du jour
UPDATE views_by_day SET views = views + 1
  WHERE product_id = 'p-run-001' AND day = '2026-06-21';
Une table counter ne contient que des counters (en plus de la clé). Impossible de mélanger une colonne counter et une colonne text hors clé.

Crée un script d'init du schéma exécuté au démarrage :

javascript · server/scripts/initCassandra.js
const cassandra = require('cassandra-driver')

async function initSchema() {
  // Connexion SANS keyspace pour pouvoir le créer
  const sys = new cassandra.Client({
    contactPoints: [process.env.CASSANDRA_HOST || '127.0.0.1'],
    localDataCenter: process.env.CASSANDRA_DC || 'datacenter1',
  })
  await sys.execute(`CREATE KEYSPACE IF NOT EXISTS sportshopy
    WITH replication = {'class':'SimpleStrategy','replication_factor':1}`)
  await sys.execute('USE sportshopy')
  await sys.execute(`CREATE TABLE IF NOT EXISTS product_views (
    product_id text, view_time timestamp, session_id text,
    PRIMARY KEY ((product_id), view_time))
    WITH CLUSTERING ORDER BY (view_time DESC)`)
  await sys.execute(`CREATE TABLE IF NOT EXISTS views_by_day (
    product_id text, day date, views counter,
    PRIMARY KEY ((product_id), day))`)
  await sys.shutdown()
}
module.exports = initSchema

Solution analyticsService

Code final validé. Essaie d'abord — ne regarde ici qu'en cas de blocage.

server/services/analyticsService.js

javascript · solution complète
const client = require('../config/cassandra')

function todayDate() {
  return new Date().toISOString().slice(0, 10) // 'YYYY-MM-DD'
}

async function recordView(productId, sessionId) {
  await client.execute(
    'INSERT INTO product_views (product_id, view_time, session_id) VALUES (?, ?, ?)',
    [productId, new Date(), sessionId],
    { prepare: true }
  )
  await client.execute(
    'UPDATE views_by_day SET views = views + 1 WHERE product_id = ? AND day = ?',
    [productId, todayDate()],
    { prepare: true }
  )
}

async function getRecentViews(productId, limit = 10) {
  const rs = await client.execute(
    'SELECT view_time, session_id FROM product_views WHERE product_id = ? LIMIT ?',
    [productId, limit], { prepare: true }
  )
  return rs.rows.map(r => ({ viewTime: r.view_time, sessionId: r.session_id }))
}

async function getViewsByDay(productId) {
  const rs = await client.execute(
    'SELECT day, views FROM views_by_day WHERE product_id = ?',
    [productId], { prepare: true }
  )
  return rs.rows.map(r => ({
    day: r.day.toString(),
    views: Number(r.views), // counter → Long → Number
  }))
}

async function getTopProducts() {
  // Démo TP : agrégat applicatif sur le jour courant.
  // En prod : table dédiée triée, ou Spark.
  const rs = await client.execute(
    'SELECT product_id, views FROM views_by_day WHERE day = ? ALLOW FILTERING',
    [todayDate()], { prepare: true }
  )
  return rs.rows
    .map(r => ({ productId: r.product_id, views: Number(r.views) }))
    .sort((a, b) => b.views - a.views)
    .slice(0, 5)
}

module.exports = { recordView, getRecentViews, getViewsByDay, getTopProducts }
À propos d'ALLOW FILTERING : on l'utilise ici pour la démo pédagogique du top produits. En production c'est un anti-pattern (scan de toutes les partitions). La bonne solution : une table top_views_by_day avec day en partition key, qu'on lit d'une seule traite.

⚡ Cheatsheet CQL + cassandra-driver

CQL · Cheatsheet
// ── KEYSPACE / TABLE ──────────────────────────────────
CREATE KEYSPACE ks WITH replication = {...};
USE ks; DESCRIBE TABLES; DESCRIBE TABLE t;

// ── ÉCRITURE (INSERT = UPSERT) ────────────────────────
INSERT INTO t (...) VALUES (...);
UPDATE t SET cnt = cnt + 1 WHERE pk = ? AND ck = ?; // counter
INSERT INTO t (...) VALUES (...) USING TTL 86400; // expiration

// ── LECTURE (WHERE = partition key) ───────────────────
SELECT * FROM t WHERE pk = ?;
SELECT * FROM t WHERE pk = ? AND ck > ? LIMIT 10;

// ── DRIVER NODE ───────────────────────────────────────
await client.execute(cql, params, { prepare: true });
rs.rows // tableau de lignes

Glossaire Cassandra

20 termes essentiels du modèle orienté colonnes et de son écosystème distribué.

01Keyspace
Plus haut niveau de regroupement, équivalent d'une base de données. Porte la stratégie de réplication.
concept
02Wide-column
Modèle où chaque ligne d'une partition peut avoir un grand nombre de colonnes ; les « lignes larges » sont idéales pour les séries temporelles.
concept
03Partition key
Partie de la PRIMARY KEY hachée pour décider du nœud de stockage. Regroupe physiquement les lignes.
modèle
04Clustering column
Colonne qui trie les lignes à l'intérieur d'une partition (ex. par timestamp DESC).
modèle
05PRIMARY KEY
= (partition key, clustering columns). Identifie une ligne et conditionne ce qu'on peut filtrer.
modèle
06CQL
Cassandra Query Language. Syntaxe proche de SQL mais sans JOIN ni WHERE arbitraire.
cql
07cqlsh
Shell interactif pour exécuter du CQL contre un nœud Cassandra.
cql
08Node / Nœud
Instance Cassandra. Tous les nœuds sont égaux (pas de maître).
archi
09Ring
Topologie en anneau où la responsabilité des données est répartie entre nœuds.
archi
10Coordinator
Nœud qui reçoit une requête client et la route vers les bons nœuds. N'importe lequel peut jouer ce rôle.
archi
11Replication factor
Nombre de copies de chaque donnée dans le cluster (RF=3 en prod, RF=1 en TP).
archi
12Consistency level
Nombre de réplicas devant répondre : ONE, QUORUM, ALL. Réglable par requête.
archi
13Datacenter
Regroupement logique de nœuds. Par défaut datacenter1 ; requis par le driver Node.
archi
14Counter
Type spécial supportant l'incrément atomique distribué (x = x + 1). Idéal pour les compteurs de vues.
cql
15UPSERT
En Cassandra, INSERT écrase silencieusement si la clé existe : insert et update sont la même opération.
cql
16Dénormalisation
Duplication volontaire des données dans plusieurs tables, une par requête. Bonne pratique ici.
modèle
17Query-first
Méthodologie : lister les requêtes d'abord, puis concevoir une table par requête.
modèle
18Hot partition
Partition recevant une charge disproportionnée à cause d'une partition key mal choisie. À éviter.
modèle
19ALLOW FILTERING
Force un scan coûteux pour des requêtes non couvertes par la clé. Anti-pattern en production.
cql
20TTL
USING TTL : expiration automatique d'une ligne après N secondes. Utile pour purger les vieux événements.
cql
