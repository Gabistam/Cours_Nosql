Le modèle Graphe

Neo4j stocke les données comme un réseau de nœuds reliés par des relations. Là où SQL doit faire des jointures coûteuses pour suivre des liens, le graphe les parcourt nativement. Cas d'usage roi : les recommandations — « les clients qui ont vu ce produit ont aussi vu… ».

⚡ Pourquoi un graphe pour les recommandations ?

Recommander, c'est suivre des chaînes de relations : produit → catégorie → autres produits, ou produit → sessions → autres produits vus. C'est exactement ce qu'un graphe fait sans effort.

CritèreSQL relationnelNeo4j (graphe)
Suivre une relationJOIN (coûteux en profondeur)Traversée native
« Amis d'amis » / co-vusJointures imbriquées lentesPattern direct en Cypher
SchémaRigide, migrations lourdesFlexible (labels + propriétés)
Lisibilité de la requêteVerbeuxVisuel, proche du dessin
VisualisationTablesGraphe interactif
Règle empirique : Neo4j quand les relations sont la donnée importante (recommandations, réseaux sociaux, détection de fraude, chemins). À éviter pour du stockage tabulaire simple ou des agrégats massifs.

🧩 Les briques du modèle graphe

⬤
Nœud (Node)
Une entité

Représente une chose : un produit, une catégorie, une session. Porte un ou plusieurs labels (:Product) et des propriétés ({id, name, price}).

➜
Relation (Relationship)
Un lien orienté et typé

Connecte deux nœuds, toujours avec un type (:IN_CATEGORY) et une direction. Peut elle aussi porter des propriétés (ex. un poids, une date).

🏷️
Label
Le « type » d'un nœud

Groupe les nœuds par rôle (:Product, :Category). Un nœud peut avoir plusieurs labels. Sert à cibler les requêtes et à indexer.

🔑
Propriété
Paire clé-valeur

Données stockées sur un nœud ou une relation : name: "Nike Pegasus", price: 129.99. Pas de schéma rigide imposé.

⌨️ Cypher — le langage en « ASCII-art »

Cypher décrit des motifs visuels. Un nœud s'écrit entre parenthèses (p:Product), une relation entre crochets fléchés -[:IN_CATEGORY]->. La requête ressemble au dessin du graphe.

cypher · les bases
// Créer un nœud
CREATE (p:Product {id: 'p-run-001', name: 'Nike Pegasus', price: 129.99})

// Créer une relation entre deux nœuds existants
MATCH (p:Product {id: 'p-run-001'}), (c:Category {name: 'running'})
CREATE (p)-[:IN_CATEGORY]->(c)

// Lire : tous les produits d'une catégorie
MATCH (p:Product)-[:IN_CATEGORY]->(:Category {name: 'running'})
RETURN p.name, p.price
MERGE = « CREATE si absent, sinon MATCH ». Pour seeder un graphe sans doublons, on utilise MERGE plutôt que CREATE : il évite de recréer un nœud déjà présent.

🛒 Le modèle de SportShopy

Trois types de nœuds et leurs relations suffisent pour les recommandations :

:Session —:VIEWED→ :Product —:IN_CATEGORY→ :Category
ÉlémentTypeRôle
:ProductNœudUn produit du catalogue (id, name, price)
:CategoryNœudUne des 6 catégories
:SessionNœudUne session de visite (réutilise le sessionId)
:IN_CATEGORYRelationProduct → Category (similarité structurelle)
:VIEWEDRelationSession → Product (similarité comportementale)
Deux stratégies de reco : structurelle (même catégorie) et comportementale (« co-vus » via les sessions). La seconde est plus pertinente mais demande des données de navigation.

🧭 Traversée vs jointure : l'avantage clé

En SQL, trouver les « produits co-vus » exige de joindre la table des vues à elle-même, ce qui devient lent à mesure que les données grossissent. En Cypher, c'est un seul motif qui se lit naturellement :

cypher · produits co-vus
MATCH (p:Product {id: $id})<-[:VIEWED]-(:Session)-[:VIEWED]->(reco:Product)
WHERE reco.id <> $id
RETURN reco.id, count(*) AS score
ORDER BY score DESC LIMIT 4
Lecture : « les produits vus dans les mêmes sessions que p, classés par nombre de sessions communes ». Un graphe rend cette logique lisible et performante.

Étape 3 — Seeder le graphe

🌱
server/scripts/seedGraph.js
Créer ce fichier — produits + catégories depuis data/products.json

Ce script est appelé au démarrage du serveur (server.js). Il reconstruit le graphe à partir du catalogue JSON existant : un nœud :Product par produit, un nœud :Category par catégorie, et la relation :IN_CATEGORY.

javascript · server/scripts/seedGraph.js
const driver = require('../config/neo4j')
const products = require('../../data/products.json')

async function seedGraph() {
  const session = driver.session()
  try {
    // Contraintes d'unicité — évite les doublons au re-seed
    await session.run('CREATE CONSTRAINT IF NOT EXISTS FOR (p:Product) REQUIRE p.id IS UNIQUE')
    await session.run('CREATE CONSTRAINT IF NOT EXISTS FOR (c:Category) REQUIRE c.name IS UNIQUE')

    for (const p of products) {
      await session.run(
        `MERGE (c:Category {name: $category})
         MERGE (p:Product {id: $id})
         SET p.name = $name, p.price = $price, p.image = $image
         MERGE (p)-[:IN_CATEGORY]->(c)`,
        { id: p.id, name: p.name, price: p.price, image: p.image, category: p.category }
      )
    }
    console.log(`🌱 ${products.length} produits seedés dans le graphe Neo4j`)
  } finally {
    await session.close()
  }
}

module.exports = seedGraph
MERGE vs CREATE : MERGE est idempotent — relancer le seed n'ajoute pas de doublons. CREATE créerait un doublon à chaque redémarrage.

Étape 4 — Service + route de recommandations

🧠
server/services/recommendationService.js
Créer ce fichier — 2 fonctions

Deux stratégies de recommandation : structurelle (même catégorie) et comportementale (co-vus dans les mêmes sessions).

javascript · server/services/recommendationService.js
const neo4j = require('neo4j-driver')
const driver = require('../config/neo4j')

// Produits de la même catégorie
async function getSimilarProducts(productId, limit = 4) {
  const session = driver.session()
  try {
    const result = await session.run(
      `MATCH (p:Product {id: $id})-[:IN_CATEGORY]->(:Category)<-[:IN_CATEGORY]-(reco:Product)
       WHERE reco.id <> $id
       RETURN reco.id AS id, reco.name AS name, reco.price AS price, reco.image AS image
       LIMIT $limit`,
      { id: productId, limit: neo4j.int(limit) }
    )
    return result.records.map(r => ({
      id: r.get('id'), name: r.get('name'),
      price: r.get('price'), image: r.get('image'),
    }))
  } finally { await session.close() }
}

// Produits vus dans les mêmes sessions (collaboratif)
async function getAlsoViewed(productId, limit = 4) {
  const session = driver.session()
  try {
    const result = await session.run(
      `MATCH (p:Product {id: $id})<-[:VIEWED]-(:Session)-[:VIEWED]->(reco:Product)
       WHERE reco.id <> $id
       RETURN reco.id AS id, reco.name AS name, reco.price AS price, reco.image AS image,
            count(*) AS score
       ORDER BY score DESC LIMIT $limit`,
      { id: productId, limit: neo4j.int(limit) }
    )
    return result.records.map(r => ({
      id: r.get('id'), name: r.get('name'),
      price: r.get('price'), image: r.get('image'),
      score: r.get('score').toNumber(),
    }))
  } finally { await session.close() }
}

module.exports = { getSimilarProducts, getAlsoViewed }
Pièges driver : les entiers en paramètre LIMIT doivent être wrappés avec neo4j.int(). Les entiers renvoyés (count(*)) sont des objets Integer Neo4j → appelle .toNumber().

Étape 5 — Démarrage du serveur

🚀
server/server.js
Modifier — ajouter l'init Neo4j après Cassandra

Le fichier server.js démarre les connexions dans l'ordre : MongoDB (bloquant), puis Cassandra et Neo4j (non-bloquants si erreur).

javascript · server/server.js — complet
const app = require('./app')
const { connectDB } = require('./config/database')
const { PORT } = require('./config/env')
const neo4jDriver = require('./config/neo4j')
const seedGraph = require('./scripts/seedGraph')
const initCassandra = require('./scripts/initCassandra')

// Redis se connecte en arrière-plan — son import suffit
require('./config/redis')

async function start() {
  await connectDB()                             // MongoDB — bloquant
  try { await initCassandra() }                  // Cassandra — non-bloquant
  catch (e) { console.error('⚠️ Cassandra non prête :', e.message) }
  try {
    await neo4jDriver.verifyConnectivity()       // vérifie la connexion Bolt
    await seedGraph()                            // MERGE produits dans le graphe
    console.log('✅ Neo4j connecté')
  } catch (e) {
    console.error('⚠️ Neo4j non disponible :', e.message)
  }
  app.listen(PORT, () => {
    console.log(`🚀 SportShopy API — http://localhost:${PORT}/api/health`)
  })
}

start().catch(err => {
  console.error('❌ Démarrage impossible :', err.message)
  process.exit(1)
})

// Fermeture propre du driver à l'arrêt
process.on('SIGINT', async () => {
  await neo4jDriver.close()
  process.exit(0)
})
Ordre important : connectDB() est awaité — le serveur ne démarre pas tant que Mongo n'est pas joignable. Cassandra et Neo4j sont dans des try/catch pour rester non-bloquants.

Ex 5
Requête en profondeur 2 — « amis des amis »
Niveau avancé · ~15 min · Cypher pur

La recommandation structurelle actuelle cherche les produits de la même catégorie (1 saut). Enrichis-la avec une requête à 2 sauts : produits de la même catégorie que les produits co-vus.

  1. Dans le Browser, écris la requête Cypher qui, pour un produit $id, trouve les produits de la même catégorie que les co-vus (2 sauts : Product → Category ← Product ← Session → Product).
  2. Ajoute une fonction getDeepRecommendations(productId, limit) dans recommendationService.js qui exécute cette requête et déduplique les résultats.
  3. Ajoute la route GET /api/recommendations/:id/deep et teste-la avec curl.
cypher · piste pour la requête profondeur 2
MATCH (p:Product {id: $id})
      -[:IN_CATEGORY]->(:Category)
      <-[:IN_CATEGORY]-(cocat:Product)
      <-[:VIEWED]-(:Session)
      -[:VIEWED]->(reco:Product)
WHERE reco.id <> $id AND cocat.id <> $id
RETURN DISTINCT reco.id, reco.name
LIMIT $limit
La requête profondeur 2 peut être lente sur un grand graphe sans index. En production, on limite le nombre de sauts et on utilise GDS (Graph Data Science) pour les algorithmes de similarité à grande échelle.
Ex 6
Bonus — Contraintes & index
Niveau expert · ~15 min · Administration Neo4j

Le script seedGraph.js crée des contraintes d'unicité, mais Neo4j peut faire plus. Explore les commandes d'administration :

  1. Dans le Browser, exécute SHOW CONSTRAINTS — liste les contraintes créées par le seed.
  2. Crée un index sur la propriété name des produits pour accélérer les recherches par nom :
    CREATE INDEX product_name_idx IF NOT EXISTS FOR (p:Product) ON (p.name)
  3. Vérifie avec SHOW INDEXES que l'index est bien créé et actif (ONLINE).
  4. Utilise EXPLAIN devant une requête MATCH (p:Product {name: 'Nike'}) pour voir si l'index est utilisé dans le plan d'exécution.
  5. Nettoyage : écris la commande pour supprimer tous les nœuds :Session et leurs relations (utile pour recommencer les exercices 3 et 4 à zéro).
MATCH (s:Session) DETACH DELETE s — DETACH DELETE supprime le nœud et toutes ses relations. Sans DETACH, Neo4j refuse de supprimer un nœud qui a encore des relations.

const driver = require('../config/neo4j')
const products = require('../../data/products.json')

async function seedGraph() {
  const session = driver.session()
  try {
    for (const p of products) {
      await session.run(
        `MERGE (c:Category {name: $category})
         MERGE (p:Product {id: $id})
         SET p.name = $name, p.price = $price
         MERGE (p)-[:IN_CATEGORY]->(c)`,
        { id: p.id, name: p.name, price: p.price, category: p.category }
      )
    }
    console.log(`🌱 ${products.length} produits dans le graphe`)
  } finally {
    await session.close()
  }
}

javascript · solution complète
const neo4j = require('neo4j-driver')
const driver = require('../config/neo4j')

async function getSimilarProducts(productId, limit = 4) {
  const session = driver.session()
  try {
    const result = await session.run(
      `MATCH (p:Product {id: $id})-[:IN_CATEGORY]->(:Category)
         <-[:IN_CATEGORY]-(reco:Product)
        WHERE reco.id <> $id
        RETURN reco.id AS id, reco.name AS name, reco.price AS price
        LIMIT $limit`,
      { id: productId, limit: neo4j.int(limit) }
    )
    return result.records.map(r => ({
      id: r.get('id'),
      name: r.get('name'),
      price: r.get('price'),
    }))
  } finally {
    await session.close()
  }
}

async function getAlsoViewed(productId, limit = 4) {
  const session = driver.session()
  try {
    const result = await session.run(
      `MATCH (p:Product {id: $id})<-[:VIEWED]-(:Session)-[:VIEWED]->(reco:Product)
        WHERE reco.id <> $id
        RETURN reco.id AS id, reco.name AS name,
            count(*) AS score
        ORDER BY score DESC LIMIT $limit`,
      { id: productId, limit: neo4j.int(limit) }
    )
    return result.records.map(r => ({
      id: r.get('id'),
      name: r.get('name'),
      score: r.get('score').toNumber(), // Integer Neo4j → Number
    }))
  } finally {
    await session.close()
  }
}

module.exports = { getSimilarProducts, getAlsoViewed }
Pièges du driver : les entiers passés en paramètre LIMIT doivent être wrappés avec neo4j.int(...), et les entiers renvoyés (count(*)) sont des objets Integer → utilise .toNumber(). Pense aussi à require('neo4j-driver') en haut pour accéder à neo4j.int.

Glossaire Neo4j

20 termes essentiels du modèle graphe et du langage Cypher.

01Nœud (Node)
Entité du graphe (un produit, une catégorie). Porte des labels et des propriétés.
concept
02Relation
Lien orienté et typé entre deux nœuds (:IN_CATEGORY). Peut porter des propriétés.
concept
03Propriété
Paire clé-valeur sur un nœud ou une relation (price: 129.99).
concept
04Label
« Type » d'un nœud (:Product). Sert à cibler et indexer. Un nœud peut en avoir plusieurs.
modèle
05Cypher
Langage de requête de Neo4j, descriptif et visuel (« ASCII-art » des motifs).
cypher
06Pattern
Motif décrivant nœuds et relations : (a)-[:R]->(b). Cœur de toute requête Cypher.
cypher
07MATCH
Recherche des motifs existants dans le graphe (équivalent du SELECT).
cypher
08CREATE
Crée des nœuds/relations. Attention : peut créer des doublons si mal utilisé.
cypher
09MERGE
« CREATE si absent, sinon MATCH ». Idéal pour seeder sans doublon.
cypher
10RETURN
Définit ce que la requête renvoie (propriétés, nœuds, agrégats).
cypher
11SET
Ajoute ou modifie une propriété sur un nœud/relation.
cypher
12Traversée
Parcours des relations pour atteindre des nœuds liés. L'opération native (et rapide) du graphe.
modèle
13Direction
Sens d'une relation : ->, <- ou non orienté - dans le motif.
modèle
14Degré
Nombre de relations d'un nœud. Un fort degré peut signaler un produit « hub ».
modèle

Protocole binaire de Neo4j (port 7687) utilisé par les drivers comme neo4j-driver.

Le driver (un seul, pool de connexions) ouvre des session courtes par requête.
