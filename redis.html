Le modèle Clé-Valeur

Redis stocke tout en RAM sous forme de paires clé→valeur. Pas de schéma, pas de jointure, pas de disque sur le chemin critique. Résultat : des latences en microsecondes là où MongoDB prend des millisecondes.

⚡ Pourquoi Redis pour le panier ?

Le panier d'achat a des exigences très différentes du catalogue produits :

CritèreMongoDB (catalogue)Redis (panier)
Durée de viePermanent (catalogue stable)Temporaire — 24h max
Latence~2–10 ms< 1 ms
StructureDocuments complexes imbriquésPaire simple clé → JSON
RelationsCatalogue, catégories, avisAucune — sessionId→panier
ExpirationManuelle (champ date)Natif (TTL)
Volume20 produits (stable)1 clé par session active
Règle empirique : Redis quand les données sont éphémères (sessions, paniers, cache, rate limiting) et que la latence est critique. MongoDB quand les données sont persistantes et structurées.

🗂️ Les 5 types de données Redis

📝
String
Le type de base — utilisé dans SportShopy

Une clé → une valeur texte (ou JSON sérialisé). C'est le type qu'on utilise pour le panier : on sérialise le tableau d'items en JSON et on le stocke dans une clé cart:{sessionId}.

redis cli
SET cart:abc123 '{"items":[]}' EX 86400
GET cart:abc123
TTL cart:abc123 # secondes restantes
🗃️
Hash
Objet structuré (champs:valeurs)

Idéal pour les profils utilisateurs ou sessions enrichies. Chaque champ est accessible individuellement sans désérialiser tout l'objet.

redis cli
HSET user:42 name "Alice" email "a@b.com"
HGET user:42 name
HGETALL user:42
📋
List
File / pile ordonnée

Liste doublement chaînée. Parfaite pour les files d'attente (FIFO avec LPUSH + RPOP) ou les historiques d'activité.

redis cli
LPUSH queue:emails "msg1" "msg2"
RPOP queue:emails # dépile FIFO
LRANGE queue:emails 0 -1
🔗
Set
Ensemble sans doublons

Collection de chaînes uniques sans ordre garanti. Idéal pour les tags, les utilisateurs connectés, ou les systèmes de vote (un utilisateur = un vote).

redis cli
SADD online:users "alice" "bob" # ajoute (ignore les doublons)
SISMEMBER online:users "alice" # 1 si présent, 0 sinon
SMEMBERS online:users # tous les membres
SREM online:users "bob" # retirer un membre
🔢
Sorted Set
Ensemble ordonné par score

Ensemble de membres triés par un score numérique. Idéal pour les classements, leaderboards, ou tags populaires.

redis cli
ZADD leaderboard 1500 "Alice" # score 1500
ZADD leaderboard 2300 "Bob" # score 2300
ZRANGE leaderboard 0 -1 WITHSCORES REV # top scores (décroissant)

💾 Persistance — RDB vs AOF

Redis est in-memory mais propose deux mécanismes de persistance pour survivre aux redémarrages :

MécanismeCommentAvantageInconvénient
RDB (snapshot)Dump binaire périodiqueCompact, rapide au redémarragePerd les données depuis le dernier snapshot
AOF (Append Only File)Log de toutes les écrituresPerte de données minimaleFichier plus volumineux
Les deuxRDB + AOF activésMeilleure garantieConfig plus lourde
Dans SportShopy, le docker-compose utilise --appendonly yes (AOF activé). Pour un panier, perdre quelques secondes de données est acceptable — mais c'est une bonne habitude de l'activer dès le dev.

📄 Comprendre le docker-compose.yml

📄
docker-compose.yml · racine du projet
Ce fichier existe déjà — la commande le lit, elle ne le crée pas

Le fichier docker-compose.yml est déjà présent à la racine du projet. docker compose up le lit pour savoir quels conteneurs lancer et comment les configurer. Il faut comprendre ce qu'il contient avant de lancer la commande.

yaml · docker-compose.yml (bloc Redis)
redis:
  image: redis:7-alpine # image officielle Redis, Alpine = légère (~50 Mo vs 120 Mo)
  container_name: sportshopy-redis # nom fixe → utilisé par docker exec et les logs
  ports: ['6379:6379'] # port_hôte:port_conteneur — ton app accède via localhost:6379
  volumes: ['redis_data:/data'] # données persistées même après docker compose down
  command: redis-server --appendonly yes # active la persistance AOF (rejeu du log au redémarrage)

redis-commander:
  image: rediscommander/redis-commander:latest # UI web pour visualiser les données
  environment:
    - REDIS_HOSTS=local:redis:6379 # ⚠ "redis" = nom du service Docker, pas localhost
  ports: ['8081:8081']
  depends_on: [redis] # garantit que redis démarre en premier
Pourquoi redis et non localhost dans REDIS_HOSTS ? À l'intérieur du réseau Docker, les conteneurs se joignent par leur nom de service (ici redis). localhost ne pointe que vers le conteneur lui-même. Ton application Node.js utilise bien localhost:6379 car elle tourne en dehors de Docker.

➕
Créer une clé — le workflow Add Key
Le même formulaire pour les 5 types

Toutes les créations passent par le bouton + Add Key. Le formulaire s'adapte selon le type choisi.

1
Cliquer sur + Add Key dans la barre du haut
Un formulaire s'ouvre à droite ou en panneau latéral selon la version de Commander.
2
Choisir le type dans le menu déroulant
String, List, Set, Hash ou Sorted Set (ZSet) — le formulaire s'adapte immédiatement.
3
Saisir le nom de la clé
Convention : namespace:identifiant — ex : user:42, cart:session-abc, tags:p-run-001.
4
Définir le TTL (optionnel)
En secondes. Laisser vide ou -1 = clé permanente. Ex : 300 = 5 min · 86400 = 24h.
5
Valider — la clé apparaît dans le panneau gauche
Pour les types composés (Hash, List, Set, Sorted Set), la clé est créée vide. Clique dessus pour ouvrir l'éditeur et ajouter les premières valeurs.

Exo C — List : historique de navigation
Séquence ordonnée — l'index d'insertion est conservé

Objectif : créer une List, ajouter des éléments, observer l'indexation et comprendre la réindexation lors d'une suppression.

1
Créer la List
+ Add Key → Type : List · Nom : historique:sess-abc · TTL : 3600
Premier élément (champ Value) : p-run-001
2
Ajouter 2 éléments supplémentaires
Dans l'éditeur List → "+ Add element" :
p-foot-003 puis p-fit-007
L'index est affiché à gauche de chaque élément (commence à 0).
3
Observer l'ordre d'affichage
Commander affiche les éléments avec leur index : [0], [1], [2]. L'ordre dépend du côté d'insertion (tête ou queue). Note l'index de chaque produit.
4
Supprimer l'élément du milieu et observer la réindexation

3️⃣
Exo 3 — Compteur atomique avec INCR
Incrémenter un entier sans risque de race condition

Objectif : découvrir INCR, opération atomique qui lit ET incrémente en une seule commande — parfait pour des compteurs de vues ou de visites.

redis cli
# Créer le compteur (la clé n'a pas besoin d'exister au préalable)
INCR vues:produit:p-run-001
INCR vues:produit:p-run-001
INCR vues:produit:p-run-001

# Lire le compteur
GET vues:produit:p-run-001

# Incrémenter de 5 d'un coup
INCRBY vues:produit:p-run-001 5

# Résultat attendu : "8"
Pourquoi atomique ? Si deux requêtes HTTP arrivent en même temps et font GET + SET, l'une peut écraser l'autre. INCR est une opération unique : Redis garantit qu'aucune autre commande ne s'intercale entre la lecture et l'écriture.

6️⃣
Exo 6 — List : file d'attente FIFO
Simuler une file d'e-mails à envoyer

Objectif : utiliser le type List comme file d'attente — LPUSH ajoute en tête, RPOP retire en queue (ordre FIFO).

redis cli
# Ajouter 3 e-mails à envoyer (LPUSH : ajout en tête de liste)
LPUSH queue:emails "email-1:bienvenue"
LPUSH queue:emails "email-2:confirmation"
LPUSH queue:emails "email-3:promo"

# Voir tous les éléments (0 -1 = du début à la fin)
LRANGE queue:emails 0 -1

# Connaître la taille de la file
LLEN queue:emails

# Consommer le 1er e-mail entré (RPOP : retire en queue = FIFO)
RPOP queue:emails
RPOP queue:emails
LRANGE queue:emails 0 -1
1) "email-3:promo"
2) "email-2:confirmation"
3) "email-1:bienvenue"

RPOP → "email-1:bienvenue" ← premier entré, premier sorti
Pattern worker : en prod, un process "worker" fait RPOP en boucle pour traiter les messages. Redis garantit qu'un message n'est consommé qu'une seule fois — même avec plusieurs workers en parallèle.

Exo 9 — Sorted Set : leaderboard
Ensemble ordonné par score — Redis maintient le tri automatiquement

Objectif : utiliser le Sorted Set pour un classement par score. Contrairement au Set, chaque membre a un score numérique et Redis maintient l'ordre automatiquement à chaque ajout ou modification — sans re-tri manuel.

redis cli
# Ajouter des membres avec leur score
ZADD leaderboard 1500 "Alice"
ZADD leaderboard 2300 "Bob"
ZADD leaderboard 980 "Charlie"

# Top 3 du meilleur au moins bon (REV = décroissant)
ZRANGE leaderboard 0 -1 WITHSCORES REV

# Score d'un membre précis
ZSCORE leaderboard "Alice" # → "1500"

# Rang d'Alice (0-indexé, ordre croissant)
ZRANK leaderboard "Alice" # → 1 (Charlie=0, Alice=1, Bob=2)

# Alice gagne 1000 points → score devient 2500
ZINCRBY leaderboard 1000 "Alice"
ZRANGE leaderboard 0 -1 WITHSCORES REV # classement mis à jour automatiquement
ZRANGE leaderboard 0 -1 WITHSCORES REV ← après ZINCRBY
1) "Alice"
2) 2500

Étape 3 — Service métier

Toute la logique Redis est concentrée dans ce fichier. Les routes ne touchent jamais Redis directement.

Ce service implémente toutes les opérations CRUD sur le panier. Clé Redis : cart:{sessionId} → valeur JSON String avec TTL 24h renouvelé à chaque écriture.

javascript · server/services/cartService.js
const redis = require('../config/redis')

// Constante TTL — une seule modification pour changer la durée de vie du panier
const TTL = 60 * 60 * 24 // 86400 secondes = 24h

// Convention : namespace:identifiant — "cart:" isole les clés du panier
const key = (sid) => `cart:${sid}`

async function getCart(sessionId) {
  const raw = await redis.get(key(sessionId)) // null si absent ou expiré
  const cart = raw ? JSON.parse(raw) : { items: [] } // Redis stocke des strings
  return _withTotals(cart)
}

async function addToCart(sessionId, product, qty = 1) {
  const cart = await _load(sessionId)
  const existing = cart.items.find(i => i.productId === product.productId)
  if (existing) existing.quantity += qty // incrémente si déjà présent
  else cart.items.push({ ...product, quantity: qty })
  await _save(sessionId, cart)
  return _withTotals(cart)
}

async function updateQuantity(sessionId, productId, quantity) {
  const cart = await _load(sessionId)
  if (quantity <= 0) {
    cart.items = cart.items.filter(i => i.productId !== productId) // qty=0 → suppression
  } else {
    const item = cart.items.find(i => i.productId === productId)
    if (item) item.quantity = quantity
  }
  await _save(sessionId, cart)
  return _withTotals(cart)
}

async function removeFromCart(sessionId, productId) {
  const cart = await _load(sessionId)
  cart.items = cart.items.filter(i => i.productId !== productId)
  await _save(sessionId, cart)
  return _withTotals(cart)
}

async function clearCart(sessionId) {
  await redis.del(key(sessionId)) // DEL supprime la clé entièrement
  return { items: [], total: 0, count: 0 }
}

async function getCartSummary(sessionId) {
  const raw = await redis.get(key(sessionId))
  if (!raw) return { count: 0, total: 0 }
  const cart = JSON.parse(raw)
  return {
    count: cart.items.reduce((s, i) => s + i.quantity, 0),
    total: +cart.items.reduce((s, i) => s + i.price * i.quantity, 0).toFixed(2),
  }
}

// ── Fonctions privées (préfixe _ = usage interne uniquement) ──────────

async function _load(sessionId) {
  const raw = await redis.get(key(sessionId))
  return raw ? JSON.parse(raw) : { items: [] }
}

async function _save(sessionId, cart) {
  // 'EX' + TTL : renouvelle le TTL à chaque écriture (sliding window 24h)
  await redis.set(key(sessionId), JSON.stringify(cart), 'EX', TTL)
}

// count et total calculés à la volée — pas stockés pour éviter les désynchronisations
function _withTotals(cart) {
  return {
    items: cart.items,
    count: cart.items.reduce((s, i) => s + i.quantity, 0),
    total: +cart.items.reduce((s, i) => s + i.price * i.quantity, 0).toFixed(2),
  }
}

module.exports = { getCart, addToCart, updateQuantity, removeFromCart, clearCart, getCartSummary }
Pourquoi JSON String et non Hash Redis ? Le panier est toujours lu/écrit en entier — un seul GET suffit. Un Hash nécessiterait plusieurs HGET. La String JSON est plus simple ici.

Étape 6 — État global React

Le panier est partagé dans toute l'app via un Context React — tous les composants y accèdent sans prop drilling.

Context + Reducer pour gérer l'état du panier. Au premier rendu, charge le panier depuis Redis via l'API.

jsx · client/src/context/CartContext.jsx
import { createContext, useContext, useEffect, useReducer } from 'react'
import * as api from '../services/cartService'

const CartContext = createContext(null)

const init = { items: [], count: 0, total: 0, loading: false }

function reducer(state, action) {
  switch (action.type) {
    case 'SET': return { ...state, ...action.cart, loading: false }
    case 'LOADING': return { ...state, loading: true }
    default: return state
  }
}

export function CartProvider({ children }) {
  const [cart, dispatch] = useReducer(reducer, init)

  // Charge le panier Redis au premier rendu (sessionId → clé Redis)
  useEffect(() => {
    api.getCart().then(c => dispatch({ type: 'SET', cart: c })).catch(() => {})
  }, [])

  // set() passe par l'API puis met à jour le state local
  const set = (promise) => {
    dispatch({ type: 'LOADING' })
    promise
      .then(c => dispatch({ type: 'SET', cart: c }))
      .catch(() => dispatch({ type: 'SET', cart: cart }))
  }

  const addToCart = (product, qty = 1) => set(api.addToCart(product, qty))
  const updateQuantity = (productId, qty) => set(api.updateQuantity(productId, qty))
  const removeFromCart = (productId) => set(api.removeFromCart(productId))
  const clearCart = () => set(api.clearCart())

  return (
    <CartContext.Provider value={{ cart, addToCart, updateQuantity, removeFromCart, clearCart }}>
      {children}
    </CartContext.Provider>
  )
}

export function useCart() {
  const ctx = useContext(CartContext)
  if (!ctx) throw new Error('useCart must be used inside <CartProvider>')
  return ctx
}
Pourquoi useReducer et non useState ? Le panier a deux états interdépendants (items + loading). useReducer centralise les transitions d'état dans une seule fonction reducer, plus lisible qu'un setState imbriqué.

const redis = require('../config/redis')

const TTL = 60 * 60 * 24 // 24h
const key = (sid) => `cart:${sid}`

async function getCart(sessionId) {
  const raw = await redis.get(key(sessionId))
  return _withTotals(raw ? JSON.parse(raw) : { items: [] })
}

async function addToCart(sessionId, product, qty = 1) {
  const cart = await _load(sessionId)
  const existing = cart.items.find(i => i.productId === product.productId)
  if (existing) existing.quantity += qty
  else cart.items.push({ ...product, quantity: qty })
  await _save(sessionId, cart)
  return _withTotals(cart)
}

async function updateQuantity(sessionId, productId, quantity) {
  const cart = await _load(sessionId)
  if (quantity <= 0) cart.items = cart.items.filter(i => i.productId !== productId)
  else { const item = cart.items.find(i => i.productId === productId); if (item) item.quantity = quantity }
  await _save(sessionId, cart)
  return _withTotals(cart)
}

async function removeFromCart(sessionId, productId) {
  const cart = await _load(sessionId)
  cart.items = cart.items.filter(i => i.productId !== productId)
  await _save(sessionId, cart)
  return _withTotals(cart)
}

async function clearCart(sessionId) {
  await redis.del(key(sessionId))
  return { items: [], total: 0, count: 0 }
}

async function getCartSummary(sessionId) {
  const raw = await redis.get(key(sessionId))
  if (!raw) return { count: 0, total: 0 }
  const cart = JSON.parse(raw)
  return {
    count: cart.items.reduce((s,i) => s + i.quantity, 0),
    total: +cart.items.reduce((s,i) => s + i.price * i.quantity, 0).toFixed(2),
  }
}

async function _load(sid) {
  const raw = await redis.get(key(sid))
  return raw ? JSON.parse(raw) : { items: [] }
}
async function _save(sid, cart) {
  await redis.set(key(sid), JSON.stringify(cart), 'EX', TTL)
}
function _withTotals(cart) {
  return {
    items: cart.items,
    count: cart.items.reduce((s,i) => s + i.quantity, 0),
    total: +cart.items.reduce((s,i) => s + i.price * i.quantity, 0).toFixed(2),
  }
}

module.exports = { getCart, addToCart, updateQuantity, removeFromCart, clearCart, getCartSummary }
Pourquoi sérialiser en JSON String et non Hash Redis ? Le panier est toujours lu/écrit en entier. Une String JSON est plus simple et évite les commandes HSET/HGET multiples. Un Hash serait pertinent si on lisait souvent un seul champ.

Glossaire Redis

Les 20 termes incontournables pour parler Redis sans hésiter.

01In-memory
Redis stocke toutes les données en RAM. Pas de lecture disque sur le chemin critique → latences en microsecondes. Contrepartie : la capacité est limitée par la mémoire disponible et les données sont volatiles sans persistance activée.
concept
02TTL
Time To Live — durée en secondes avant expiration automatique d'une clé. Redis supprime la clé sans intervention externe. Dans SportShopy, le panier expire après 86 400 s (24h) d'inactivité. Commandes : EXPIRE key n / option EX n du SET.
commande
03Clé-Valeur
Modèle de stockage le plus simple : une chaîne de caractères unique (clé) pointe vers une valeur. La clé est arbitraire — par convention on utilise des séparateurs (:) pour créer des espaces de noms : cart:abc, user:42:prefs.
concept
04String
Type Redis de base. Valeur jusqu'à 512 Mo. Peut contenir du texte, du JSON sérialisé, des nombres entiers (atomiquement incrémentés avec INCR), ou des données binaires. C'est le type utilisé pour le panier dans SportShopy.
type
05Hash
Objet Redis avec plusieurs champs : HSET key field value. Idéal pour les profils utilisateurs ou sessions enrichies. Permet de lire/écrire un seul champ sans désérialiser tout l'objet — avantage sur la String JSON quand les champs sont souvent accédés séparément.
type
06List
Liste doublement chaînée. LPUSH / RPUSH pour ajouter, LPOP / RPOP pour retirer. Parfaite pour les files d'attente FIFO (LPUSH + RPOP), les historiques ou les flux d'activité récente.
type
07Set
Ensemble de chaînes sans doublons. SADD / SMEMBERS / SISMEMBER. Utile pour les tags uniques, les utilisateurs connectés, ou les systèmes de vote (un utilisateur = un vote).
type
08Sorted Set
Set ordonné par un score numérique. ZADD / ZRANGE / ZRANK. Parfait pour les classements, leaderboards, ou tags populaires triés par fréquence d'utilisation.
type
09EXPIRE / EX
EXPIRE key seconds définit ou renouvelle le TTL d'une clé existante. L'option EX de SET combine création et TTL en une commande atomique : SET key val EX 3600. Dans cartService, chaque écriture renouvelle le TTL (comportement "sliding window").
commande
10RDB
Redis Database Backup — snapshot binaire compressé de toutes les données, sauvegardé périodiquement sur disque. Rapide au redémarrage mais peut perdre les données depuis le dernier snapshot. Activé par défaut dans Redis.
concept
11AOF
Append Only File — log de toutes les commandes d'écriture. Reconstruit l'état exact lors d'un redémarrage. Perte de données minimale (dernière seconde). Activé dans SportShopy via --appendonly yes dans docker-compose.
infra
12Session
Identifiant unique associant un visiteur à ses données côté serveur. Dans SportShopy, le sessionId est un UUID généré côté client (crypto.randomUUID()) et stocké dans localStorage. Il est transmis via le header x-session-id.
concept
13Cache
Stocker temporairement le résultat d'une opération coûteuse pour éviter de la recalculer. Redis est la solution de cache la plus utilisée : résultats de requêtes MongoDB, réponses d'API externes, pages HTML générées. TTL = durée de validité du cache.
concept
14ioredis
Client Redis le plus populaire pour Node.js. Supporte les promesses nativement, la reconnexion automatique, les pipelines, les clusters et Sentinel. Alternative : redis (client officiel), plus simple mais moins de fonctionnalités avancées.
outil
15Redis Commander
Interface web open-source pour explorer et modifier les données Redis. Visualise les clés, valeurs, TTL et types. Lancé via Docker dans SportShopy sur le port 8081. À ne jamais exposer en production.
outil
16Pub/Sub
Mécanisme de messagerie Redis : un publisher envoie sur un canal (PUBLISH), des subscribers reçoivent en temps réel (SUBSCRIBE). Utile pour les notifications push, le chat, la synchronisation entre microservices. Non utilisé dans cette phase mais courant en production.
concept
17Pipeline
Mécanisme ioredis qui regroupe plusieurs commandes en un seul aller-retour réseau. Au lieu d'envoyer 5 commandes séparément (5 allers-retours), on les pipeline et on attend une seule réponse groupée. Gain de latence significatif pour les opérations en lot.
outil
18Atomicité
Redis exécute chaque commande de manière atomique — elle ne peut pas être interrompue à mi-chemin par une autre commande. INCR par exemple lit ET incrémente en une seule opération. Pour grouper plusieurs commandes atomiques : MULTI / EXEC (transactions Redis).
concept
19Eviction Policy
Comportement de Redis quand la mémoire est pleine. Politiques courantes : allkeys-lru (supprime les clés les moins récemment utilisées), volatile-lru (idem mais seulement les clés avec TTL), noeviction (erreur en écriture). Configuré via maxmemory-policy.
infra
20SCAN
Alternative à KEYS * pour la production. SCAN cursor MATCH pattern COUNT n itère sur les clés par lots sans bloquer Redis. KEYS * scanne toutes les clés d'un coup et peut bloquer le serveur sur un gros dataset — à éviter en prod.
commande
